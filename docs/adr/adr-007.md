# ADR 0007: Flüchtige Prompt-Zellen zur KI-gestützten Inhalts- und Code-Generierung

* **Status:** Akzeptiert
* **Datum:** 2026-09-25
* **Kontext:** Rosida (Interaktive Datenanalyse, Markdown/Qmd-Dateiformat, KI-Assistenz)

---

## 1. Kontext und Problemstellung

Die interaktive Arbeit mit Data-Science-Bibliotheken (Polars, Matplotlib, SymPy) profitiert erheblich von natürlichsprachlicher Unterstützung (z. B. Syntaxkonstruktion für komplexe Filter oder Aggregationen).

Das Einführen eines persistenten Zelltyps „Prompt“ birgt jedoch schwerwiegende Nachteile für ein dateibasiertes Notebook-System:

* **Verlust der Reproduzierbarkeit:** Wird ein Dokument bei jedem Durchlauf („Run All“) live gegen eine LLM-API ausgeführt, liefert dieselbe Datei je nach Modellstand und Temperatur unterschiedliche Ergebnisse.
* **Bruch der Offline-Fähigkeit:** Das Dokument ließe sich ohne Internetzugang oder aktive lokale Inferenz-Engine nicht mehr vollständig rendern oder ausführen.
* **Format-Bloat:** Ein proprietärer Zelltyp widerspricht der Philosophie von Rosida, Dokumente als sauberes, portables Markdown (`.md` / `.qmd`) ohne proprietären JSON-Ballast abzuspeichern.

---

## 2. Architekturentscheidung

Wir implementieren Prompt-Zellen als **flüchtiges Interaktionsmuster (Transient State)**. Ein Prompt fungiert rein als Erzeugungswerkzeug im Frontend und persistiert nicht im Dokumentenmodell.

```text
┌────────────────────────────────────────────────────────┐
│ [Prompt]                                               │
│ "Selektiere aus df alle Personen mit age > 21"        │
└──────────────────────────┬─────────────────────────────┘
                           │  Ctrl+Enter (API-Call)
                           ▼
┌────────────────────────────────────────────────────────┐
│ [Markdown]  (Automatisch umgewandelt)                  │
│ Gefiltertes DataFrame für volljährige Personen:        │
│                                                        │
│ ```python                                              │
│ df_adults = df.filter(pl.col("age") > 21)              │
│ ```                                                    │
└────────────────────────────────────────────────────────┘
                           │ (Optional manuell durch User)
                           ▼
┌────────────────────────────────────────────────────────┐
│ [Python]                                               │
│ df_adults = df.filter(pl.col("age") > 21)              │
└────────────────────────────────────────────────────────┘

```

### 2.1 Konvertierung in Markdown

1. Die Zelle wird temporär in den Zustand `Prompt` versetzt.
2. Nach dem Absenden (`Ctrl+Enter`) schickt Rosida die Anfrage an die Inferenz-Schnittstelle.
3. Sobald die Antwort vorliegt, **wird die Zelle unmittelbar zu einer regulären `Markdown`-Zelle**.
4. Der Inhalt wird durch den generierten Text ersetzt. Liefert das Modell Codeblöcke (````python ... ````), bleiben diese syntaktisch hervorgehoben und für den Nutzer sofort les- und überprüfbar.
5. Der Nutzer behält die volle Kontrolle: Er kann die Markdown-Erklärung stehen lassen, den Codeblock herauskopieren oder die gesamte Zelle bei Bedarf per Zelltyp-Umschalter direkt in eine ausführbare `Python`-Zelle überführen.

### 2.2 Zero-Dependency Inferenz-Client

Um das AppImage und die Windows-Pakete schlank zu halten, wird auf externe SDKs (wie `openai`, `anthropic`, `langchain`) verzichtet.

* Die Anbindung erfolgt über eine minimalistische HTTP-Implementierung (Standardbibliothek `urllib.request`).
* Als Standard-Schnittstelle dient das universelle OpenAI-kompatible Schema (`/v1/chat/completions`). Dies deckt lokale Server (Ollama unter `http://localhost:11434/v1`, LM Studio) sowie Hosted-Endpunkte transparent ab.
* Konfiguration erfolgt deklarativ über `~/.config/rosida/config.json` oder Umgebungsvariablen (`ROSIDA_LLM_ENDPOINT`, `ROSIDA_LLM_MODEL`).

### 2.3 Schemainjektion (Namespace-Metadaten)

Damit der Agent fehlerfreien Code mit existierenden Variablen und Spaltennamen generiert, erzeugt der laufende Kernel-Worker auf Anfrage einen schlanken System-Prompt-Auszug:

* Nur Variablennamen und Schemata werden übertragen (z. B. `df: polars.DataFrame(cols=['name': String, 'age': Int64])`).
* Es werden **keine Zeilendaten oder privaten Dateiinhalte** an die Schnittstelle übermittelt.

---

## 3. Konsequenzen

### Positiv

* **100 % Reproduzierbarkeit:** Das resultierende Dokument enthält ausschließlich festen Text und deterministischen Code.
* **Volle Portabilität:** Gespeicherte `.md`-Dateien bleiben unabhängig von externen APIs in jedem Standard-Editor vollständig lesbar.
* **Kein Vendor-Lock-in:** Funktioniert nahtlos mit lokalen Open-Source-Modellen (Ollama) auf dem Entwicklungsrechner.
* **Sicherheit:** Der Nutzer sieht den generierten Code zwingend vor der eigentlichen Ausführung im Editor (keine blinde Remote-Code-Execution).

### Negativ / Mehraufwand

* **Manueller Zwischenschritt:** Möchte der Nutzer sofort nur den reinen Code ausführen, muss er den Codeblock kopieren oder die Zelle auf den Typ `Python` umschalten und den Begleittext entfernen.
* **Netzwerk- und Timeout-Handling:** Timeouts oder Verbindungsfehler bei nicht erreichbarem Ollama-Daemon müssen über das System-Log (ADR 0006) gemeldet werden, ohne den Zellinhalt zu verwerfen.
