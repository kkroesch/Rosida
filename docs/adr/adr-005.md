# ADR 0005: Isolierte Code-Ausführung via persistenten QProcess und dynamische Toolbar-Steuerung

* **Status:** Akzeptiert
* **Datum:** 2026-09-25
* **Kontext:** Rosida (Ausführungsumgebung, Kernel-Architektur, UI/UX)

---

## 1. Kontext und Problemstellung

Die Ausführung von Python-Code in interaktiven Notebooks birgt inhärente Risiken für Stabilität und Responsivität der Anwendung:

* **UI-Blockaden:** Berechnungsintensive Operationen (z. B. Polars-Pipelines, Matplotlib-Rendering, komplexe Algorithmen) blockieren bei synchroner Ausführung den Qt-Event-Loop des Main-Threads.
* **Unkontrollierbare Schleifen:** In-Process-Threading (`QThread`) erlaubt in CPython keinen verlässlichen, sicheren Abbruch laufender Endlosschleifen (`while True`) oder blockierender nativer C-/Rust-Extensions. Ein erzwungenes Beenden via OS-Thread-Kill führt regelmäßig zu Deadlocks, Speicherlecks oder dem Absturz des gesamten Programms samt Datenverlust.
* **Toolbar-Ergonomie:** Ein permanenter, meist inaktiver Stop-Button erzeugt visuellen Ballast im SDI-Fenster.

---

## 2. Architekturentscheidung

Wir entkoppeln die Code-Ausführung vollständig vom GUI-Hauptprozess und binden die Laufzeitkontrolle an einen modalen Zustand der Werkzeugleiste:

### 2.1 Persistenter Subprozess (`QProcess`)

* Jedes geöffnete Dokument instanziiert genau einen langlebigen Subprozess (`python -u kernel_worker.py`).
* Der Worker hält den fortlaufenden Namensraum (`locals`/`globals`), sodass Variablen, Imports und DataFrames zellenübergreifend erhalten bleiben.
* Die Kommunikation zwischen GUI und Worker erfolgt asynchron und zeilenbasiert über Standard-Streams (`stdin`/`stdout`) via NDJSON (Newline Delimited JSON).

### 2.2 Zweistufige Abbruch-Strategie

Beim Triggern eines Abbruchs durch den Benutzer greift eine Kaskade:

1. **Stufe 1 (Kooperativ):** Senden von `SIGINT` (POSIX) bzw. `CTRL_C_EVENT` (Windows) an den Subprozess. Löst eine `KeyboardInterrupt`-Exception im Worker aus; der bestehende Python-Zustand bleibt nach Möglichkeit erhalten.
2. **Stufe 2 (Erzwungen):** Reagiert der Prozess innerhalb eines Timeouts (1,5 Sekunden) nicht, wird er hart via `QProcess::kill()` beendet. Der Host startet automatisch einen frischen Worker-Prozess und markiert den Kernel-Status als zurückgesetzt.

### 2.3 Modale UI-Aktionen (Run / Run All / Stop)

Die Toolbar implementiert eine strikte Zustandsmaschine:

| Zustand | Action: `Run` | Action: `Run All` |
| --- | --- | --- |
| **Idle** | Aktiviert (▶ Einzelzelle ausführen) | Aktiviert (⏩ Alle Zellen ausführen) |
| **Executing** | Deaktiviert (`disabled`) | Umfunktioniert zu **Stopp** (⬛ Quadrat, bricht Kernel ab) |

---

## 3. Konsequenzen

### Positiv

* **Stabilität der UI:** Die GUI bleibt jederzeit voll responsiv, unabhängig von Auslastung oder Hängern im Nutzeroberflächen-Code.
* **Prozess-Isolation:** Schwerwiegende Fehler (Segfaults in C-Bibliotheken, Memory Exhaustion, Aufrufe von `os._exit()`) reißen nicht das Rosida-Hauptfenster mit um.
* **Sauberes Minimal-UI:** Kein redundanter Stop-Button; die Intention "alles ausführen" wird während der Laufzeit logisch durch "Ausführung stoppen" ersetzt.
* **SDI-Konformität:** Jeder Dokumenten-Host besitzt seinen eigenen OS-Prozess-Lifecycle, ohne Quereffekte auf andere Fenster.

### Negativ / Mehraufwand

* **IPC-Overhead:** Daten (Outputs, Fehlermeldungen, formatierte Tabellen) müssen serialisiert werden. Große Payloads (DataFrames) erfordern effiziente Transferformate (z. B. Arrow IPC/Parquet statt reinem String-Dumping).
* **Prozessverwaltung:** Saubere Bereinigung verwaister Subprozesse (Zombie-Prozesse) beim Schließen des Fensters oder bei unerwartetem Programmende muss gewährleistet sein (`QProcess`-Parenting und Signal-Handling).
